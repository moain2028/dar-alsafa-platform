# التشغيل والنشر والتحقق

## بيئات مقترحة

- **local:** SQL.js + SEED_DEMO=true؛ للتطوير والاختبار فقط.
- **staging:** PostgreSQL وRedis، مستخدمون غير حقيقيين، ZATCA sandbox/compliance، مزود دفع test mode.
- **production:** PostgreSQL مُدار ونسخ احتياطي، Redis، KMS/HSM، أسرار مدارة، WAF، مراقبة وتنبيهات، وحسابات إنتاج معتمدة.

## قائمة الإطلاق

1. مراجعة `docs/REQUIREMENTS.md` وإغلاق المتطلبات المطلوبة تجارياً بدلاً من افتراض اكتمال العرض.
2. تعطيل seed وتغيير الحسابات وإصدار JWT secret عشوائي (32+ بايت) وتدوير أي سر سابق.
3. تطبيق migration، `DB_SYNCHRONIZE=false`، اختبار restore للنسخة الاحتياطية.
4. ضبط `WEB_ORIGIN` و`NEXT_PUBLIC_API_URL` وHTTPS وCORS، وعدم كشف قاعدة البيانات أو Redis للإنترنت.
5. إضافة مستخدمين حقيقيين بأقل صلاحية، وتفعيل MFA على مستوى الهوية عند توفره.
6. إتمام ZATCA compliance وonboarding وتوقيع XML وفق `docs/ZATCA.md`.
7. إتمام مزود الدفع والتحقق من webhook signature وidempotency والمصالحة، وعدم الوثوق بنتيجة العميل.
8. اختبارات حمل وسقوط PostgreSQL/Redis ومزود الدفع، واختبار اختراق وصلاحيات بين الفروع.
9. مراقبة health وerror rate وlatency وqueue backlog، وخطة rollback ومنع فقدان الطلبات.
10. تدريب الإدارة والكاشير والمطبخ والمناديب وتوثيق إجراءات الاسترداد والورديات والدعم.

## فحص صحة سريع

```bash
curl -fsS https://API_HOST/api/health
npm run typecheck && npm run lint && npm test && npm run build
```

## الترقية والنسخ الاحتياطي

- لقطة قاعدة قبل كل migration، ونشر API قبل الويب عند توافق خلفي.
- لا تستخدم `--force` أو synchronize في الإنتاج.
- راجع سجل التدقيق والقيود غير المتوازنة (يجب أن تكون صفراً) بعد النشر.
- احتفظ بسجلات الفوترة والطلبات وفق المتطلبات النظامية، مع سياسة وصول وإتلاف موثقة.

## مؤشرات خدمة قابلة للقياس

لا تُعلن نسبة توافر قبل قياسها. ابدأ بأهداف داخلية قابلة للمراقبة: نسبة نجاح إنشاء الطلب، زمن p95 لكل endpoint، زمن بث التغيير، عمق طوابير الدفع/ZATCA، وفشل OTP والمصالحة. اربط التنبيهات بفريق مناوب وخطة تصعيد قبل توقيع SLA 24/7.
